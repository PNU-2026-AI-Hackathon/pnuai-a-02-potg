# ProgramCase 정규화 및 기획서 생성 AI 결정 기록

> **문서 상태 — 결정 기록:** 이 문서에서 제안한 프로그램 단위 검색 프로필과 기획안 생성 연계는 현재 구현되었습니다. 운영 흐름은 [MOIRA Studio AI 기획 과정](../ai-data/MOIRA_STUDIO_AI_PLANNING.md), 검색 계약은 [MOIRA Studio 검색 명세](../specs/MOIRA_STUDIO_RETRIEVAL.md)를 확인하세요.

## 문서 목적

이 문서는 ProgramCase 의미 검색 MVP를 검증한 뒤 논의해 확정한 후속 방향을 정리합니다. 웹 ChatGPT 또는 새 작업 담당자에게 전달할 수 있는 기획·기술 컨텍스트입니다.

## 현재까지 확인한 사실

- 크롤링 원본과 개인정보가 제거된 Document/Chunk는 정상적으로 구축됐습니다.
- KURE-v1 임베딩 888건과 pgvector 검색은 기술적으로 정상 작동합니다.
- ProgramCase 중복 제거와 Top 5 API/UI도 정상 작동합니다.
- 그러나 현재 검색은 CORE, SESSIONS, ATTACHMENT 청크를 독립적으로 비교합니다.
- 작은도서관 프로그램에는 어린이, 체험, 창의, 교육, 독서 같은 공통 표현이 많습니다.
- 프로그램의 핵심 의미와 홍보·행정·첨부 주변 문장이 충분히 분리되지 않아 유사도 점수가 밀집합니다.
- 특히 ATTACHMENT 청크가 대표 결과를 과도하게 차지할 수 있습니다.

따라서 문제의 중심은 임베딩 모델 자체보다 `무엇을 임베딩하는가`에 있습니다.

## 합의된 제품 방향

MOIRA Studio의 목표는 단순 문서 검색이 아니라 사용자의 자연어 아이디어와 유사한 기존 프로그램 사례를 제안하고, 선택된 사례를 참고해 정형화된 프로그램 기획서 초안을 만드는 것입니다.

권장 사용자 흐름은 다음과 같습니다.

```text
자유로운 자연어 아이디어 입력
→ 정형화된 유사 ProgramCase 5개 제안
→ 사용자가 사례를 선택하거나 전체 추천을 수락
→ AI가 입력에서 빠진 조건만 2~3개 질문
→ 정형화된 기획서 초안 생성
→ 참고한 유사 사례 함께 표시
```

사용자는 추가 질문을 건너뛰고 현재 정보만으로 초안을 생성할 수 있어야 합니다. 처음부터 긴 설문을 강제하지 않습니다.

## 데이터 계층 설계

기존 DB를 폐기하거나 원본을 덮어쓰지 않습니다.

```text
원본 계층
ProgramCase / Session / Attachment / 추출 본문
        ↓
정규화 계층
ProgramCaseSearchProfile
        ↓
검색 계층
ProgramCase당 대표 검색 문서와 대표 embedding 1개
```

기존 Chunk와 embedding은 원본 근거 탐색, 상세 참고자료, 기준선 비교에 유지할 수 있습니다. 최종 유사 ProgramCase 선정에서는 정규화된 대표 프로필을 우선 사용합니다.

## ProgramCaseSearchProfile 초안

```json
{
  "programCaseId": "uuid",
  "title": "똑똑한 지구인 프로젝트",
  "summary": "초등학생이 기후변화와 탄소중립을 체험으로 배우는 프로그램",
  "topics": ["ENVIRONMENT", "CLIMATE", "SCIENCE"],
  "targetAgeGroups": ["ELEMENTARY"],
  "objectives": ["기후변화 이해", "환경 실천 습관 형성"],
  "activityTypes": ["EXPERIMENT", "DISCUSSION", "CRAFT"],
  "activities": ["기후 실험", "탄소발자국 확인", "업사이클링 만들기"],
  "operationTypes": ["EXPERIENTIAL", "MULTI_SESSION"],
  "sessionCount": 6,
  "sessionSummary": "기후 이해부터 생활 속 실천까지 6회 운영",
  "searchKeywords": ["환경 교육", "기후위기", "탄소중립", "과학 체험"]
}
```

초기 스키마는 실제 349건의 분포를 분석한 뒤 확정합니다. 하나의 프로그램은 여러 주제와 활동 유형을 가질 수 있어야 하며 근거가 없으면 `UNKNOWN` 또는 빈 배열을 사용합니다.

## 전처리 원칙

### 포함할 정보

- 프로그램 제목
- 대상과 연령대
- 핵심 주제
- 프로그램 목적
- 실제 주요 활동
- 활동 및 운영 형태
- 회차 수와 회차 구성 요약
- 검색용 핵심어와 표준 동의어

### 제외할 정보

- 개인정보와 연락처
- 신청·모집 상태와 행정 안내
- 도서관 공통 홍보 문구
- 반복되는 인사말과 저작권 안내
- 프로그램 의미와 관계없는 첨부 양식 문구
- 근거 없이 추정한 효과와 활동

## LLM 사용 원칙

LLM은 필수 구성요소가 아닙니다. 정형화된 데이터를 자연스러운 문장으로 다시 작성하기 위해 LLM을 호출하지 않습니다. 임베딩용 텍스트는 다음처럼 결정적 템플릿으로 생성할 수 있습니다.

```text
프로그램명: 똑똑한 지구인 프로젝트
대상: 초등학생
핵심 주제: 환경, 기후, 과학
목적: 기후변화를 이해하고 환경 실천 습관을 기른다
주요 활동: 기후 실험, 탄소발자국 확인, 업사이클링 만들기
활동 형태: 실험, 토론, 공예
운영 형태: 체험형 다회차
회차 구성: 기후 이해부터 생활 속 실천까지 6회 운영
검색어: 환경 교육, 기후위기, 탄소중립, 과학 체험
```

LLM은 비정형 원본에서 목적과 주요 활동처럼 규칙으로 추출하기 어려운 값을 고정 JSON 스키마로 구조화할 때만 선택적으로 사용합니다.

권장 우선순위는 다음과 같습니다.

```text
제목·대상·회차·기간 → 결정적 규칙
주제 동의어 → taxonomy 사전
목적·주요 활동 → 규칙으로 부족한 경우 LLM 보조
임베딩 문서 → 결정적 템플릿
```

LLM 출력은 허용 taxonomy, 원문 근거, 길이, 개인정보, hallucination을 검증하며 model, prompt version, schema version, source hash를 기록합니다.

## 검색 알고리즘 방향

온라인 검색은 모든 metadata를 무조건 hard filter로 사용하지 않습니다.

```text
사용자 자연어 요청
→ 요구 조건 구조화 + query embedding
→ 명확한 필수 조건만 hard filter
→ 정규화된 ProgramCase 대표 벡터와 유사도 검색
→ keyword 및 metadata soft boost
→ 넓은 후보군 약 20개 확보
→ 조건, 완성도, 유사도, 중복을 고려해 최종 3~5개 선정
→ LLM 기획서 생성의 참고 사례로 사용
```

대상, 부모-자녀 참여, 단회차/다회차처럼 사용자가 명확하게 요구한 조건은 hard filter 후보입니다. 환경, 과학, 문화처럼 복수 분류와 누락 가능성이 큰 주제는 초기에는 soft boost가 안전합니다.

사용자에게는 유사 ProgramCase 5개를 제안하고, 선택된 5개 전체를 기획서 생성의 참고자료로 사용합니다. 각 사례를 서로 다른 고정 역할로 나눌 필요는 없지만 거의 동일한 사례만 반복 선정되지 않도록 후보 단계에서 중복과 다양성을 고려합니다.

## 기획서 생성 결과

최종 결과는 정형화된 형태로 제공합니다.

- 프로그램명
- 기획 배경
- 목적
- 대상 및 인원
- 운영 기간과 회차
- 회차별 활동
- 준비물과 필요 인력
- 예산 초안
- 기대 효과
- 성과 측정 방법
- 운영·안전 유의사항
- 참고한 유사 ProgramCase

사용자 입력에서 확정된 내용, 기존 사례에서 참고한 내용, AI가 제안한 내용, 추가 확인이 필요한 내용을 구분합니다. 기존 사례의 날짜, 연락처, 인원, 예산을 현재 기획의 사실처럼 복사하지 않습니다.

## 후속 이슈 권장 범위

전체 349건을 즉시 가공하지 않고 작은 파일럿으로 판단합니다.

1. 운영 DB를 변경하지 않는 349건 데이터 분포 분석
2. 주제, 대상, 활동, 운영 형태의 초기 taxonomy 제안
3. ProgramCaseSearchProfile 스키마 설계
4. 대표 사례 30~50건 선정
5. 규칙 기반 정규화 프로필 생성
6. 선택적으로 LLM 구조화 버전 생성
7. 결정적 대표 검색 문서와 대표 embedding 생성
8. 현재 Chunk P0, 규칙 프로필, LLM 보조 프로필 비교
9. 수동 정답 질의 20~30개로 Top 5 평가
10. 전체 처리 및 운영 검색 교체 여부 결정

## 비교 실험

다음 세 방식을 같은 데이터와 질의로 비교합니다.

- A: 현재 Chunk 기반 P0 검색
- B: 규칙 기반 정규화 + 결정적 템플릿
- C: 규칙 기반 정규화 + 선택적 LLM 추출 + 결정적 템플릿

평가 항목은 Top 5 주제 적합도, 대상 일치도, 부적합 결과 수, 다양성, 원문에 없는 정보 생성 여부, 처리 비용, 재현성입니다. B가 충분히 좋으면 LLM을 사용하지 않고, C가 명확하게 개선하는 필드에만 LLM을 제한합니다.

## 현재 브랜치의 최종 의미

현재 브랜치는 실패가 아니라 검색 기준선을 확립한 작업입니다.

- 임베딩 저장과 pgvector 검색이 정상 작동함을 확인
- 원본 DB 무결성과 개인정보 보호를 검증
- 자연어 검색 API와 수동 테스트 UI 구축
- Chunk 검색의 ATTACHMENT 편향과 점수 밀집을 확인
- 최종 기획서 생성 검색에는 ProgramCase 단위 정규화가 필요하다는 근거 확보

따라서 현재 브랜치는 종료하고, 위 후속 범위는 새 이슈와 새 브랜치에서 시작합니다.
