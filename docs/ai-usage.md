# AI 도구 활용 및 고도화

> 제7회 PNU 창의융합 AI 해커톤 · 융합트랙 2팀 · 팀 POTG

우리는 AI를 최종 판단자가 아니라 **주민 의견과 도서관 프로그램 기획을 연결하는 보조 도구**로 활용하였다. **개발 과정**에서는 분석·구현·검증·문서화를 함께 수행하는 개발 보조 도구로, **서비스 내부**에서는 기획안 초안 생성과 유사 사례 탐색을 돕는 기능으로 사용하였다.

## 1. 활용한 AI 도구

| 구분 | 도구 | 활용 내용 |
| --- | --- | --- |
| 개발 보조 | ChatGPT, Claude, Codex, GitHub Copilot | 기존 코드·데이터 구조 분석, 구현 초안, 오류 원인 분석, 테스트·검증 CLI, 이슈·PR·기술 문서 작성 |
| 서비스 생성 AI | Google Gemini API | MOIRA STUDIO 기획안 초안 생성과 항목 단위 문장 수정 |
| 의미 검색 | KURE-v1 / Sentence Transformers | 프로그램 사례 임베딩 생성과 pgvector 유사도 검색 |
| 문서 인식 | NAVER Cloud CLOVA OCR | 이미지·스캔 PDF 안내문의 텍스트 추출 |

여러 도구를 병행하되 결론을 여러 도구에게 검토를 시키고 최종 채택 여부(머지)는 팀원들이 함께 결정하였다.

## 2. 활용 범위

**개발 과정** — 프론트엔드 화면, 백엔드 API와 Prisma 데이터 처리, 프로그램 수집·정제 배치, 첨부파일 텍스트 추출, 의미 검색, 테스트 코드와 문서 초안 작성에 활용하였다. 작업은 `기존 구조 분석 → 변경 범위 검토 → 브랜치 단위 구현 → 테스트 → 제한 검증 → diff 검토 후 반영` 순서로 진행하였고, 요구사항과 우선순위, 데이터 구조, 반영 여부는 팀원이 결정하였다. 커밋 메시지는 AI가 작성하더라도 push와 PR 머지는 팀원이 수행하였다.

**서비스 내부** — MOIRA STUDIO는 사서가 입력한 조건과 주민 아이디어를 바탕으로 프로그램명·기획 의도·대상·운영 방식·회차 구성을 갖춘 기획안 초안을 생성한다. 생성 결과는 바로 확정되지 않으며 사서가 항목 단위로 다시 다듬을 수 있다. 정제한 프로그램 사례는 임베딩 검색을 거쳐 기획 참고자료로 제공한다.

## 3. AI 생성 코드의 검증·수정 방식

> AI가 제안하거나 작성한 코드는 즉시 운영 데이터에 반영하지 않았다. 팀원이 변경 범위와 diff를 검토하고, 타입 검사·테스트·제한된 실제 데이터 검증을 통과한 경우에만 단계적으로 반영하였다.

**① 실행 전에 작업 범위와 금지 조건을 먼저 정의하였다.** 구현에 앞서 범위를 이슈 문서로 확정하고 팀원이 이슈를 등록한 뒤에 착수하였다. 운영 DB 점검은 `BEGIN TRANSACTION READ ONLY`로 제한해 쓰기·migration·seed를 금지하였고, 비용이 발생하는 외부 API 재호출은 상한을 정해 건별로 승인하였다. 인증 키와 원문, 개인정보는 프롬프트와 보고서에 남기지 않았다.

**② 위험도에 따라 실행 범위를 단계적으로 넓혔다.** 첨부파일 처리는 fixture·mock 검증 → 외부 호출 없는 dry-run → 표본 1건 → 제한 배치 → 전체 처리 → 읽기 전용 집계 순으로 진행하였다. 최종 집계에서 활성 첨부파일 237건이 모두 `COMPLETED`, orphan 0건으로 확인되었다.

**③ 자동 검증과 사람 검수를 함께 요구하였다.** 빌드·타입 검사와 별개로 기능마다 실행 가능한 검증 스크립트(`test:*`, `verify:*` 60여 개)를 작성하게 하여 회귀 여부를 판정하였다. 정제 결과는 수집 351건, 라벨 사전 매핑률 98.4% 같은 기준 수치와 대조하였고, 검색 저장 방식을 pgvector로 옮길 때는 평가 질의 30건의 순위가 이전 결과와 30/30 일치함을 확인한 뒤 반영하였다. 동시에 첨부 검수 화면과 검색 평가 화면을 만들어 팀원이 원문과 직접 대조하였다.

**④ AI의 보고를 원본과 대조하고, 개별 수정 대신 원인을 일반화하였다.** AI가 "다운로드 실패"로 보고한 첨부 건을 원문에서 확인해 본문 `<img>` 이미지를 수집하지 못하는 크롤러 결함을 찾아냈고, OCR 진행 보고는 외부 서비스 콘솔의 호출 이력과 대조하였다. 잘못 추출된 항목은 해당 레코드만 고치지 않고 같은 원인을 가진 건을 전수 조사해 규칙으로 수정하였으며, 특정 레코드를 코드에 하드코딩하지 않는 것을 원칙으로 삼았다.

**검증하지 않은 범위** — mock 기반 테스트는 외부 API를 호출하지 않았고, 최종 집계는 원본 파일을 재다운로드해 육안 대조하지 않았다. OCR 결과는 저장 상태와 기본 품질을 확인하였을 뿐 전체 원문을 대조한 것은 아니다.

## 4. 한계와 운영 원칙

AI가 생성한 코드와 설명에는 오류 가능성이 있으며, OCR과 검색 결과는 원문 품질과 추출 정확도에 따라 달라진다. AI가 만든 기획안은 참고 초안이고 사실성과 운영 가능성을 자동으로 보장하지 않는다. 따라서 모이라는 AI 결과를 자동 확정하지 않으며, 최종 기능 범위와 데이터 반영, 배포, 프로그램 개설 여부는 팀원과 현장 담당자가 결정한다.
