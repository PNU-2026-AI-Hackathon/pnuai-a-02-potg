# 프로젝트 결정 기록

새로운 장기 결정은 각 항목에 **결정**, **이유**, **영향**을 모두 기록한다. 확인되지 않은 날짜나 결정자는 추측하지 않는다.

## 1. 게시판 기준 구조

### 결정

- 게시판의 최종 기준은 `/community/*`로 한다.
- 작은도서관 행사 및 소식, 자유게시판, 지역 제안 게시판으로 구성한다.
- `/board`와 `/api/posts`는 초기 연동 실험 또는 레거시 구현으로 분류한다.

### 이유

- `/community/*`가 현재 서비스 기획의 게시판 구분과 일치한다.
- `/board`는 메모리 기반 API를 연결한 초기 실험 구조다.

### 영향

- 이후 게시판 개발과 DB 연동은 `/community/*`를 기준으로 진행한다.
- 두 구조는 당분간 함께 존재한다.
- 이번 문서 작업에서 레거시 코드를 삭제하거나 통합하지 않는다.
- 통합과 제거는 별도 이슈에서 결정한다.

## 2. 대학생 봉사자 기능

### 결정

- 대학생 봉사자 모집 및 매칭은 현재 MVP에서 제외한다.
- 남아 있는 volunteer API와 mock 데이터는 이번 작업에서 삭제하지 않는다.

### 이유

- 현재 MVP의 핵심은 주민 제안과 작은도서관 프로그램 기획 흐름이다.
- volunteer 관련 구현은 과거 계획의 잔여 mock 수준이다.

### 영향

- `/api/volunteers`, volunteer mock 데이터, summary의 봉사 항목을 현재 기능으로 홍보하지 않는다.
- 제거 여부는 별도 이슈에서 결정한다.

## 3. Backend 기술 기준

### 결정

- Backend의 현재 기준은 Express와 TypeScript다.
- NestJS는 현재 기술 스택으로 기록하지 않는다.

### 이유

- 실제 package.json과 서버 진입점이 Express로 구현되어 있다.
- NestJS 의존성이나 모듈 구조가 없다.

### 영향

- 문서, 실행 방법, 아키텍처 설명은 Express를 기준으로 한다.
- 향후 프레임워크 변경은 별도 기술 결정과 마이그레이션 범위가 필요하다.

## 4. AI 프로그램 기획 명칭과 구현 표현

### 결정

- AI 프로그램 기획 기능의 공식 명칭은 **모이라 스튜디오**다.
- pgvector, LangChain.js, RAG, AI API는 현재 구현으로 표현하지 않는다.

### 이유

- 제품 명칭을 일관되게 사용해야 한다.
- 현재 의존성, Prisma schema, API 및 서비스 코드에서 해당 구현이 확인되지 않는다.

### 영향

- 모이라 스튜디오는 목표 기능이자 현재 미구현 기능으로 관리한다.
- AI 기술 선택과 구현은 별도 이슈와 결정 기록을 통해 확정한다.

## 5. 운영 구조와 배포 검증 범위

### 결정

- 운영 구조는 Vercel Frontend, AWS EC2 Backend, AWS RDS PostgreSQL로 기록한다.
- 통신은 브라우저에서 Next.js 서버 계층/API Route, Express, PostgreSQL 순서로 설명한다.

### 이유

- 해당 구조는 팀이 확인한 현재 운영 정보다.
- 저장소에는 배포 구성과 자동화 파일이 없다.

### 영향

- 메인 페이지 서버 컴포넌트의 Express 호출을 브라우저 직접 호출로 표현하지 않는다.
- 저장소만으로 배포를 재현하거나 검증할 수 있다고 주장하지 않는다.
- GitHub Actions 배포 자동화는 현재 없는 것으로 기록한다.

## 6. 문서와 코드의 사실 우선순위

### 결정

- 실제 코드와 최근 결정사항을 최초 개발계획서보다 우선한다.
- 현재 MVP 범위는 `CURRENT_SCOPE.md`를 최종 기준으로 한다.

### 이유

- 원본 계획에는 현재 스택과 범위에서 제외되거나 미구현인 내용이 포함되어 있다.
- AI 에이전트가 계획을 현재 사실로 오인하지 않아야 한다.

### 영향

- 충돌을 발견하면 추측하지 않고 문서에 상태 차이를 기록한다.
- 범위 변경 시 `CURRENT_SCOPE.md`, 기능 변경 시 `IMPLEMENTATION_STATUS.md`를 갱신한다.

## 7. 작업 범위와 변경 통제

### 결정

- 요청 또는 이슈 범위에 포함되지 않은 파일을 임의로 수정하지 않는다.
- 새 의존성, 실행 스크립트, workflow 변경은 이유와 영향을 먼저 확인한다.

### 이유

- package.json과 workflow의 절대 변경 금지는 정상적인 향후 개발을 방해할 수 있다.
- 반대로 문서 작업이 기능과 자동화 변경으로 확장되어서는 안 된다.

### 영향

- 이번 작업은 `AGENTS.md`, `.ai/*`, README 정리로 한정한다.
- Issue/PR 템플릿 개선, `npm run check`, GitHub Actions, AI 자동화는 별도 PR에서 진행한다.

## 8. 구현 상태 용어

### 결정

- 구현 상태는 코드 경로 구현됨, 부분 구현, mock, UI 골격, 실행 검증 필요, 미구현, MVP 제외로 구분한다.

### 이유

- 코드 존재와 실제 환경에서의 정상 동작은 같은 의미가 아니다.
- AI 에이전트와 팀원이 기능 완성도를 과대평가하지 않아야 한다.

### 영향

- 빌드, lint, DB 연결, 실제 API 테스트를 하지 않은 기능을 동작 검증 완료로 표현하지 않는다.
- 기능별 근거와 관련 Issue/PR은 `IMPLEMENTATION_STATUS.md`에서 관리한다.
